## 2. The load model

One process, one multi-thread runtime (`worker_threads` = `available_parallelism()`, recorded), 200 client tasks + 1 control task.

**Ramp.** 20 clients / 250 ms → 200 connected in 2.5 s, then 3 s settle. Each: TLS handshake, WS upgrade, `join`, await `joined`. `connect_ms` is its own distribution and is **never** inside a write number — that is where handshake cost is quarantined.

**Two runs per invocation over the same 200 connections, separated by `reset`:**

- **Run A — `burst_only` (AC-54).** `reset` → `live` → the 2 s burst immediately → drain → `close` → reconcile. **3 cycles**; each has its own p95, pooled n=600 secondary. **Headline AC-54 = the worst of the three cycle p95s.**
- **Run B — `segment` (AC-53, AC-52, AC-41).** `reset` → `live` → 20 s churn → the same 2 s burst → drain → `close` → reconcile → post-close refusal probe → **5 reveals** 2 s apart.

**The 2 s window.** The driver computes one shared `deadline: Instant` and hands it to every client at spawn — no message passing at fire time. Client *i* gets `offset_i = SplitMix64(seed, i) mod 2000ms`, uniform over `[deadline, deadline+2000ms)`, then `sleep_until` and sends exactly one answer. Uniform is the headline shape because `SPEC.md` §9 says "200 writes inside 2 s". `--burst-shape spike` (all 200 in the last 50 ms) exists and, if run, is reported in its own block labelled extra stress — never as the AC-54 number.

Every session's **final** answer is a burst write. The churn writes are the room changing its mind while `live`; the burst write is the last one and the one that must be counted.

**Upsert (AC-34, `SPEC.md` §4.3).** During churn each client sends `1 + (i mod 3)` writes at pseudo-random instants, strictly increasing `seq`, letters derived from `(i, seq)` so they spread A–E. Last write wins server-side. After `close` every client sends one more and must get `accepted:false` with its **saved** letter restated; totals re-fetched afterwards must be byte-identical to the frozen ones (§4.4).

**AC-52's oracle.** Each client holds its own final `accepted:true` letter and `seq`. After `close` the driver compares three things against the frozen totals:

1. per-letter `totals[A..E]` == the client-side expected histogram, **letter by letter**, not just the sum;
2. `answered` == 200 and `Σ totals` == 200;
3. `applied_seq_sum` (server: Σ over sessions of the applied `seq`) == Σ of each client's own final accepted `seq`.

(3) turns "no lost or duplicated per-session response" into a per-session claim **without the spike server ever exposing a per-session answer** — the throwaway stays structurally honest to AC-56. Any of the three failing is an AC-52 miss.

## 3. Measurement method

**What bounds a write.** `t_send` = immediately before `sink.send(answer)` on an already-open, already-handshaken connection; `t_ack` = when the matching `ack` (keyed by `seq`) is read off that same socket. `write_ms = t_ack − t_send`, `std::time::Instant`, **one clock, one task**. Contains local TLS encrypt + kernel + network RTT + Fly proxy + server apply. Contains **no** connect, no handshake, no upgrade.

`send_lag_ms = t_send − t_scheduled` is recorded **separately and never added to write latency** — 200 real phones do not queue behind each other, so charging the laptop's scheduler to the server would be a lie in the wrong direction. It is the laptop-bottleneck detector.

**What bounds a fan-out.** `t_issue` = when the driver writes the `reveal` control frame; `t_recv_i` = when client *i* reads the broadcast. `fan_out_i = t_recv_i − t_issue`. **One clock** (driver and clients share a process), so cross-machine skew cannot enter. It over-counts by the driver→server one-way time (~½ RTT), which is conservative: it can only make AC-41 look worse. Also reported: `spread_ms` = last receipt − first receipt, which is skew-free *and* path-free and isolates the server's broadcast loop. Server-stamped times are a `clock_offset_ms_median` diagnostic only, never a headline.

**Estimator: nearest-rank on the sorted sample.** `p95 = x_(⌈0.95·n⌉)`, ascending, 1-based.

- n = 200 → **the 190th of 200** (0-based 189); exactly 10 samples at or above it.
- n ≈ 800 (full segment writes) → the 760th. n = 1000 (5 reveals × 200) → the 950th.

**Why it is trustworthy at n=200, stated rather than assumed.** The 95th percentile at n=200 is a single order statistic whose rank has binomial sampling error σ = √(n·p·(1−p)) = √9.5 ≈ 3.08 ranks. A 95% interval is rank 190 ± 1.96σ → **ranks 184 to 196**. The report therefore always prints `p95_ms` = x_(190) **and** `p95_ci_ms` = [x_(184), x_(196)] **and** `max_ms`. Enforced in code: if `p95_ms < 500` but `x_(196) ≥ 500`, the run is marked `"marginal": true` and the verdict says so in words. That is the mechanical form of *do not soften a miss*. n=200 is also why `burst_only` runs 3 cycles and AC-41 pools 1000 receipts. `p99` prints with an explicit *informational, 2 samples above it at n=200* note rather than being quietly believed.

**Report schema** (`room/spike/reports/<date>.json`, also stdout):

```

           frame_bytes, reveal_bytes }
```

Raw `samples_ms` ship in the file so the client, the code reviewer, or HC-0 can recompute every percentile independently. The report proves itself rather than asking to be believed.

**Burst reported separately from the segment**, three ways: `runs.burst_only` is its own run against a freshly reset room with no churn traffic (AC-54's *in isolation*); `runs.segment.writes` is the full population including its burst (AC-53); `runs.segment.burst_subset` carves the burst back out as a cross-check. The `criteria` array names which field each AC reads, so nobody has to guess which number is which.

**Exit codes.** The JSON is written **before** the exit code is computed, always, pass or fail.

- `0` — all four criteria pass.
- `1` — a criterion missed: `burst_only.headline_p95_ms ≥ 500`, `segment.writes.p95_ms ≥ 500`, `reveal_pooled.p95_ms > 2000`, or any AC-52 mismatch.
- `2` — **run invalid, numbers not to be quoted**: fewer than 200 clients connected; any connect/send error, ack timeout (>5 s), or missing reveal receipt; `send_lag.p95_ms > 25`; `ulimit -n < 1024`; more than one distinct `fly_machine_id` across the 200 `joined` frames.

Separating 1 from 2 is what stops a broken harness being read as a failing server, or the reverse.

## 4. Wire protocol

JSON text frames, one object per frame. Control rides a **201st WebSocket** (`role: "control"`, never joins, never counts toward capacity) — no HTTP client dependency, one transport, and the reveal-issue timestamp lands on the very same clock as every receipt.

**Client → server:** `join {session}` · `answer {session, seq, letter}` · `ping {nonce}` · `control {cmd: reset|live|close|reveal|totals}`

**Server → client:** `hello {instance, region, app, version, epoch, phase}` (on connect; `FLY_MACHINE_ID` is what proves all 200 sessions met one process) · `joined {session, present, phase, capacity}` · `refused {reason:"full"}` · **`ack {seq, letter, accepted, reason?, saved_letter?, applied_seq}`** · `phase {phase}` · **`reveal {reveal_id, answer, server_ts_ms, pad}`** · `pong {nonce, server_ts_ms}` · `control_ok {cmd, epoch, totals?, answered?, applied_seq_sum?}`

**The ack is what bounds the write.** The handler takes the room `Mutex`, applies the upsert (`answers.insert(session,(letter,seq))`, updating `applied_seq_sum`), **drops the guard, then** writes the `ack`. So the ack means *the write is in the authoritative map*, not *the frame arrived*. A write after `close` is refused in the same shape (`accepted:false, reason:"closed", saved_letter:<frozen>`) — `SPEC.md` §4.3's *refused with the saved answer restated*, three lines.

`reveal` carries a `pad` sized by `--reveal-bytes` (**default 2048**) so the fan-out is not flattered by a 60-byte frame; the real reveal payload is kilobytes. The size is recorded.

**Server state.** `Arc<Mutex<Room>>` = `{epoch, phase, answers: HashMap<String,(char,u32)>, totals: Option<[u32;5]>, answered_frozen, applied_seq_sum}` plus one `broadcast::Sender<Arc<str>>` (capacity 256). `close` computes totals once and freezes them (§4.4). `reset` bumps `epoch` and clears. Each connection is a `tokio::select!` over its socket read and its broadcast receiver; `RecvError::Lagged` is counted and surfaced in `control_ok`, so a dropped reveal can never be silently invisible. `axum::serve(listener.tap_io(|s| { let _ = s.set_nodelay(true); }), app)`. Binds `0.0.0.0:$PORT`, default 8080. No auth, no wall, no persistence, no phase machine beyond `idle → live → closed` + a reveal broadcast — **T-04a still writes the real one on a blank page.**

Control routes are unauthenticated, per the ticket's *no auth*. A throwaway app for a few minutes; a stray request would surface as an epoch/reconcile mismatch rather than a quietly wrong number. Named as a risk, not hidden.

### m-4 · `applied_seq_sum` is an aggregate, so a swap could cancel (ACCEPTED, plan changed)

**Concern.** A pooled sum across 200 sessions cannot distinguish a two-session swap from correct state, yet the plan frames it as a per-session proof.

**Resolution.** Add a fourth reconciliation check that is per-session without dumping per-session answers. The server returns `applied_fingerprint` = the XOR over sessions of `splitmix64(hash(session_id) ^ (letter_index << 32) ^ seq)`; the client computes the same from its own 200 final accepted writes. A swap between two sessions changes the fingerprint; only a genuinely identical assignment leaves it intact. Three lines on each side, the spike server still exposes no per-session answer, and AC-52's claim stops being an aggregate one. `RECON` gains `applied_fingerprint_match`, and a mismatch is an AC-52 miss (exit 1).
