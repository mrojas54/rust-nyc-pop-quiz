# Recorded workflow lessons

These are historical examples from the October 4, 2026 Rust NYC Pop Quiz review, not current project facts or defaults for future briefings. The workflow involved opening saved progress views, starting a cloud assessment, comparing scheduling alternatives, expanding dependent estimates, and entering an option in the project terminal. The recording did not establish completion of that cloud assessment or the option's downstream execution.

| Observed evidence | Reusable lesson |
| --- | --- |
| A view captured October 4 displayed “Checked Sep 29” with one completion denominator; another used a different active scope. | Capture time is not source freshness. Reconcile scope before interpreting percentages as progress or regression. |
| The dashboard distinguished board status from a merged PR. | Report the discrepancy and inspect acceptance evidence before treating the ticket as complete. |
| A view showed passed, partial, failed, and blocked criteria; another displayed passing pipeline test totals and estimated readiness. | Test totals, criterion coverage, and operational readiness measure different things. |
| The full-backlog view estimated total focused effort separately from dependency-chain effort and included one delivery route within a ticket. An alternative route added effort. | Keep full scope, chain effort, and alternatives separate; avoid counting included work twice. |
| Expanding a ticket exposed prerequisite work, credential and persistence concerns, and a downstream dependent ticket. | Read ticket detail and prerequisites rather than estimating from titles. |
| A separate event-readiness view showed a smaller critical path with deployed checks and rehearsal remaining. | Identify the delivery target before reconciling estimates; full backlog and event readiness can have different scopes. |
| “Option A” appeared as terminal keyboard input without a captured result. | Report the observed selection and leave execution unconfirmed. |
