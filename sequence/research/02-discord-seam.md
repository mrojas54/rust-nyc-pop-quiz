# Dimension 2: The External System — Discord

Research for the Rust NYC live-quiz app's host-authorization seam: Discord OAuth2 (`identify` + `guilds.members.read`) gating on the `nyc-organizers` role in the Rust East Coast guild, plus a proposed 15-minute grace window for role-check outages.

## Summary

Discord's OAuth2 endpoint for reading a user's own guild membership (`/users/@me/guilds/{guild.id}/member`) does exactly what the design needs: it returns a `roles` array of role-ID snowflakes, scoped to the guild, using only the user's own bearer token (no bot required, no bot-in-guild requirement). Role IDs are immutable and safe to hard-code; role names are not. Discord confirms Administrator/owner status does **not** appear as a role and does **not** bypass a role-ID check performed by reading `roles` — that assumption in the design is correct, because the member endpoint just returns whatever is in `roles`; owner/Administrator is a permission computed elsewhere, not a role membership fact. Refresh tokens are single-use and rotate on every refresh (confirmed via a 2023 Discord GitHub issue, closed "not planned" — i.e., intended behavior, and *not* stated in the primary docs, which is itself a gap). Access tokens live 7 days (604800s). The bigger risk is not rate limits (5-10 organizers polling occasionally is nowhere near Discord's 50 req/s global cap or the 10k-invalid-request-in-10-min ban threshold) — it's **Discord reliability**. Discord's own status history shows resolved incidents commonly running 20 minutes to 3 hours, including a login/auth-affecting global incident in May 2026 described as one of the platform's most significant recent outages. A 15-minute grace window will not cover Discord's own typical major-incident duration; it covers only the short tail.

## Objects and states — what a "member with a role" actually is

- **Guild Member Object** (`GET /users/@me/guilds/{guild.id}/member`, requires `guilds.members.read` scope): a JSON object including `user` (optional partial user object), `nick`, `roles` (array of snowflake **strings**, i.e., role IDs — not names), `joined_at` (ISO8601), and, in some contexts, `permissions` (a computed permission bitfield string; documented as populated "when in the interaction object" — not guaranteed present on this OAuth2 endpoint response). Source: [Guild resource docs](https://docs.discord.com/developers/resources/guild), [Users resource docs](https://docs.discord.com/developers/resources/user).
- `roles` is an array of role **IDs** (snowflakes), confirmed by both the Guild resource schema and general Discord developer consensus: role IDs are immutable, assigned at role creation, and are the recommended stable identifier — role **names** can be renamed by any admin at any time and must never be used for authorization. Source: [Guild resource docs](https://docs.discord.com/developers/resources/guild); community confirmation e.g. [discordjs-bot-guide roles](https://github.com/AnIdiotsGuide/discordjs-bot-guide/blob/master/understanding/roles.md).
- **Administrator permission / guild ownership do not manifest as a role.** Administrator is a permission bit on a *role* the user may or may not hold; guild ownership is a separate `owner_id` field on the guild object, not a role. Neither is reflected in the `roles` array unless the owner/admin has also been explicitly assigned the `nyc-organizers` role. This means: the design's stated intent ("must not let ownership/Administrator override the explicit role-ID check") is automatically satisfied by construction — you cannot accidentally treat an admin as authorized by reading `roles`, because `roles` simply won't contain the organizer role ID unless it was granted. The design isn't fighting an API behavior here; it's fighting a *hypothetical* the API doesn't actually present. Source: [Permissions topic](https://docs.discord.com/developers/topics/oauth2) discussion of Administrator bypassing channel overwrites — that bypass is scoped to *permission checks*, not to the contents of the `roles` array. **Caveat**: if the app's authorization code ever reads a computed `permissions` field instead of `roles` and treats "has Administrator bit" as sufficient, that would reintroduce the bypass. The design must check `roles.includes(NYC_ORGANIZERS_ROLE_ID)`, never a permission bitfield.
- **Not a member of the guild**: the endpoint's behavior on a non-member is not spelled out in Discord's primary docs (gap). Developer reports describe it 404ing since there's no member record to return. Treat "not found" as the practical expectation but verify empirically. Source: [discord-api-docs issue tracker discussion](https://github.com/discord/discord-api-docs/issues) (multiple threads on this scope; no canonical error-code table found).
- **Role removal propagation / caching**: no caching layer sits between this OAuth2 endpoint and Discord's live member state — it's a direct read, not a bot-side cache. Bot-side gateway caches (`GUILD_MEMBER_UPDATE`) are a *different* code path (bot token + gateway) and are irrelevant here since this design uses bearer-token REST calls only. **Unknown — no documented SLA on internal propagation latency for role changes reaching this specific endpoint**; treat as "should be near-immediate" but do not assume a hard guarantee. Measure empirically before relying on tight re-check intervals.

## Auth flow with real endpoint shapes

1. **Authorize**: browser redirect to `https://discord.com/oauth2/authorize` with `response_type=code`, `client_id`, `scope=identify guilds.members.read`, `redirect_uri`, and a `state` value.
2. **Token exchange**: `POST /oauth2/token` returns:
   ```json
   {
     "access_token": "...",
     "token_type": "Bearer",
     "expires_in": 604800,
     "refresh_token": "...",
     "scope": "identify guilds.members.read"
   }
   ```
   `expires_in` is fixed at 604800 seconds (7 days) for every Discord OAuth2 grant — this is documented and also confirmed as a known quirk (a GitHub issue notes it's *always* 604800 regardless of what one might expect). Source: [OAuth2 docs](https://docs.discord.com/developers/topics/oauth2), [discord-api-docs#4755](https://github.com/discord/discord-api-docs/issues/4755).
3. **`identify` scope** → `GET /users/@me`: returns the user object *without* `email` (email requires the separate `email` scope). Gives `id`, `username`, `discriminator`/`global_name`, `avatar`, etc. Source: [OAuth2 docs](https://docs.discord.com/developers/topics/oauth2).
4. **`guilds.members.read` scope** → `GET /users/@me/guilds/{guild.id}/member`: returns the Guild Member Object for the *current authenticated user* in the specified guild, using the user's own bearer token — **no bot needed, no bot presence in the guild required**. This is distinct from the bot-token member-lookup path (`GET /guilds/{guild.id}/members/{user.id}`), which does require a bot that is a member of that guild plus (for member listing) the privileged `GUILD_MEMBERS` intent. The design's chosen path (bearer-token self-lookup) sidesteps privileged-intent approval entirely, which is a real simplification worth noting explicitly in the design doc. Source: [Users resource docs](https://docs.discord.com/developers/resources/user), [discord-api-docs PR #4204](https://github.com/discord/discord-api-docs/pull/4204) (original documentation of this scope/endpoint pairing).
5. **Refresh**: `POST /oauth2/token` with `grant_type=refresh_token`. Docs describe the mechanics but do **not** state whether the refresh token rotates. Empirically (per a 2023 discord-api-docs issue, closed "not planned," i.e. Discord confirmed this is intended, not a bug): **refresh tokens are single-use and rotate on every refresh** — reusing an old refresh token returns `invalid_grant`. An app that stores a single fixed refresh token and re-uses it will break the second time it tries to refresh. Source: [discord-api-docs#5942](https://github.com/discord/discord-api-docs/issues/5942).
6. **Revocation**: `POST /oauth2/token/revoke` invalidates *both* the access and refresh token for that authorization, regardless of which one was passed. Source: [OAuth2 docs](https://docs.discord.com/developers/topics/oauth2).
7. **Re-consent**: the `prompt` parameter controls whether the user is forced back through the consent screen (`prompt=consent`) or skipped (`prompt=none`) on repeat authorizations. Scope changes (e.g., adding `guilds.members.read` to an app that previously only requested `identify`) will require existing users to re-authorize to grant the new scope — plan for this if scopes are ever added later.

## Limits (rate / token / verification)

- **Global rate limit**: 50 requests/second across the whole application. Irrelevant at 5–10 organizers.
- **Per-route limits**: bucketed by method + resource; headers `X-RateLimit-Limit`, `-Remaining`, `-Reset`, `-Reset-After`, `-Bucket`, and (on 429 only) `-Scope` (`user` | `global` | `shared`). Source: [Rate Limits docs](https://docs.discord.com/developers/topics/rate-limits).
- **429 body**: `{ message, retry_after, global }` — the app must honor `retry_after`, not guess.
- **Invalid-request ban**: an IP making **10,000+ requests in 10 minutes** that return 401/403/429 gets automatically, temporarily Cloudflare-banned from the Discord API (429s with `X-RateLimit-Scope: shared` are excluded from the count). Duration/scope of the ban isn't published beyond "temporary." For this app: the only realistic way to trip this is a bug that hot-loops retrying a failing role-check call without backoff — not membership polling at any sane cadence. Design implication: the periodic re-check during a live room **must** implement exponential backoff / respect `retry_after` on failure, or a bad deploy could self-inflict an IP-wide ban that takes down *every* organizer's session (shared hosting/server IP risk if deployed on a platform with a shared egress IP). Source: [Rate Limits docs](https://docs.discord.com/developers/topics/rate-limits).
- **Verification threshold (100 servers)**: applies to **bots** joining guilds and to privileged intents. This app has no bot and never joins a guild — it only performs user-bearer-token OAuth reads. The 75/100-server verification trigger is **not applicable** to this design as scoped. Do not let "we might need Discord verification" become a phantom blocker; it would only become relevant if the app later adds a bot component. Source: [community discussion of verification thresholds](https://github.com/discord/discord-api-docs/discussions/3971), [support-dev.discord.com](https://support-dev.discord.com/hc/en-us/articles/23926564536471-How-Do-I-Get-My-App-Verified).
- **Unknown — scope gating**: some Discord OAuth2 scopes (e.g., `rpc`) require Discord's advance approval/whitelisting per-application. No documentation was found stating `guilds.members.read` requires such approval, and its presence in the standard scope table (not flagged "requires approval") suggests it's generally available — but this should be verified empirically by actually requesting it in the Developer Portal before the design commits to it as unblocked.

## Failure modes and what the app sees

| Discord-side event | What the app observes |
|---|---|
| Discord API fully down | Connection timeout / 5xx from `discord.com`/`discordstatus.com`-reported outage. No `roles` data obtainable at all — this is the case the grace window exists for. |
| User removed from guild since last check | Endpoint likely 404s (unconfirmed in primary docs; inferred from developer reports) — treat as "not authorized," fail closed. |
| Role removed but user still in guild | Next successful call returns `roles` without the organizer role ID — fail closed on next check. |
| Access token expired (>7 days old) mid-room | 401; app must have already refreshed proactively, or the room's host loses the ability to re-auth mid-room without a fresh login (participants aren't affected, since they never authenticate). |
| Refresh token reused (bug: stored stale token) | `invalid_grant` on refresh — host is silently locked out of *future* logins until they redo the full OAuth flow; won't be visible until someone hits it. |
| 429 from role-check polling | Must back off per `retry_after`; a naive retry loop risks the 10k/10min ban described above. |

## Where the proposed design over-assumes

1. **The 15-minute grace window is short relative to Discord's own observed incident durations.** Status-page history shows multiple *resolved* incidents in the 20-minute-to-3-hour range (an "API Errors" incident ran roughly 3 hours; a billing-operations incident roughly 2.8 hours; several messaging/session incidents 15–90 minutes), and a global login-affecting outage in May 2026 was described as one of the platform's more significant recent incidents. A 15-minute window will cover *some* short blips but will not cover a genuine major Discord incident, which the data suggests happens on a scale of weeks-to-months, not never. This isn't necessarily wrong for the product (a dead room during a meetup is arguably an acceptable failure mode), but the design should state explicitly that 15 minutes is "cover the common short blip," not "cover a Discord outage" — as currently phrased it reads like an outage-tolerance number when the evidence says it's closer to a jitter-tolerance number. Source: [Discord incident history](https://discordstatus.com/history), [May 2026 outage coverage](https://easternherald.com/2026/05/09/discord-down-api-outage-global-2026/).
2. **Role-removal propagation latency to this specific REST endpoint is not documented anywhere found.** The design implicitly assumes "re-check on a schedule" will see a role removal promptly. This is very likely true (it's a direct DB-backed read, not a gateway cache) but is unverified against a primary source — flag as assumed-but-unconfirmed.
2b. **Non-member error shape is assumed, not documented.** No primary-source text was found specifying the exact status code/error body when the authenticated user has left the guild since granting the OAuth scope. Verify empirically (almost certainly 404, based on developer consensus) before writing failure-handling code that pattern-matches on a specific status.
3. **Refresh-token rotation is undocumented in the primary OAuth2 reference** but confirmed via a closed GitHub issue as intended behavior. Any implementation must persist the *new* refresh token on every refresh call — a design or implementation that assumes a stable, reusable refresh token will silently break itself after the first refresh cycle.
4. **`identify` + `guilds.members.read` is sufficient and does not need `guilds` too.** Some third-party guides suggest `guilds` (list of guilds) is needed alongside `guilds.members.read` — it is not, for a single known guild ID; `guilds.members.read` alone gates the one `/users/@me/guilds/{guild.id}/member` call this design needs. No need to request the broader `guilds` scope, which would be over-scoping relative to least-privilege.
5. **"Administrator overriding the role check" is a non-issue by construction**, as detailed above — the design's defensive language about it is safe to keep as a code-review guardrail (never read a permissions bitfield for authorization) but isn't guarding against an actual documented API behavior where Administrator injects itself into `roles`.

## Alternatives to Discord auth

For ~5–10 known organizers, Discord OAuth2 is defensible but not obviously load-bearing — it buys automatic sync with "who currently holds the role in the Discord," so an organizer added/removed in Discord doesn't require a separate admin action in this app. That's real value if the org already manages membership turnover through Discord roles. But it costs: a 7-day token lifecycle to manage, single-use refresh-token bookkeeping, an extra failure domain (Discord's uptime becomes this app's uptime ceiling for host login), and OAuth callback/CSRF surface area. A **shared secret / invite-link-with-token** (each organizer gets a bookmarked magic link with a long random token, rotated on suspicion of leak) has zero external dependency, zero outage risk, and is trivial to reason about for a group this small — the tradeoff is manual provisioning/deprovisioning and a leaked-link risk instead of a compromised-account risk. A **hard-coded allowlist keyed to Discord user ID** (still uses Discord `identify` for "who are you" but drops `guilds.members.read` and the live role check entirely, checking membership in a static list instead) keeps the familiar "log in with Discord" UX while removing the live-role-check failure mode and the grace-window problem altogether — role changes just require a one-line config update instead of propagating through Discord. A **GitHub org** membership check is a lateral move with the same shape of tradeoffs as Discord (another external IdP, another rate limit/outage surface) and no clear advantage unless the org already anchors identity in GitHub instead of Discord. Given the "grace window" complexity the current design is already contemplating, it's worth asking directly whether that complexity is buying enough over the hard-coded-allowlist-plus-Discord-identify hybrid, which would eliminate the outage-coupling problem this research surfaced while keeping the "log in with Discord" UX intact.

- What is the actual propagation latency from a Discord role removal to this endpoint reflecting it? Unknown — measure by removing a test role and timing the next successful read.
- Does requesting `guilds.members.read` require any Discord approval/whitelisting step for a new application, or is it available by default in the Developer Portal? Unknown — verify by attempting to configure it in a real Developer Portal application.
